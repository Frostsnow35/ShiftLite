一、概述 / Summary

本 PR 实现 issue #24：把「换权重即换应用」从代码挪到数据，新增 manifest 驱动的迁移对配置层（core/pairs.py + pairs/*.json），并把系统从单对 horse2zebra 扩展为四类迁移任务。同时用新增的反向对 zebra2horse 做端到端验证（setup → bench → quality → layers → Web），并用它暴露了两个方向性缺陷：数据集名不能推断权重方向、评测集目录按 zip 的 testA/testB 命名会自相矛盾。

This PR implements issue #24: it moves "swap the weights, swap the application" from code into data by introducing a manifest-driven pair layer (core/pairs.py plus pairs/*.json), and extends the system from a single horse2zebra pair to four translation types. The new reverse pair zebra2horse is used for end-to-end validation (setup → bench → quality → layers → Web) and exposed two direction-related defects: dataset names do not determine weight direction, and naming eval directories after the zip's testA/testB becomes self-contradictory.

五、风险与已知问题 / Risks & Known Issues

  1. 两个新 pair 未跑通到 benchmark：summer2winter（126 MB）与 style_monet（291 MB）的 manifest 已就位，但数据集在本机跨境链路下实测只有 40–70 KB/s，尚未完成下载；界面里显示「未就绪」。Two pairs are declared but not yet benchmarked because their datasets could not be downloaded at usable speed from this machine.
  2. 新 pair 只有 proxy 指标：本机 venv 缺 torchvision，quality --deep 跑不了，zebra2horse/quality.json 的 metrics_source 为 "proxy"，不得与默认 pair 的 real 指标同表。New pairs only carry proxy metrics; they must not be mixed with the real deep metrics of the default pair.
  3. metrics_deep 键名仍是 horse2zebra 专用（*_vs_real_zebra）。给 zebra2horse 开 --deep 前必须改成按 ref_prefix 命名，否则参照域是「马」却写着「zebra」。Deep-metric keys are still named after zebra; they must be parameterised before enabling --deep on reverse pairs.
  4. Runtime 单驻留：切换 pair 会重编译（秒级）。若后续要频繁对比，考虑 LRU=2，代价是常驻内存 +0.3–0.5 GB。Only one runtime stays resident; switching recompiles. LRU=2 is possible at the cost of extra RSS.
  5. bench 会覆盖证据文件：本次开发中确实覆盖过已入库的 benchmark.json（用 git checkout 还原）。默认 pair 的证据文件路径未变，该风险仍在。bench overwrites the committed evidence file; this actually happened during development and had to be restored.
